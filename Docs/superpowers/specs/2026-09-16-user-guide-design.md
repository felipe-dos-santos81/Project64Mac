# User guide design

## Goal

One player-facing document, `Docs/UserGuide.md`, that takes someone from a fresh clone on
an Apple Silicon Mac to playing a game, building a controller mapping with the wizard,
and playing with a mouse or a webcam. The wizard section is illustrated with one
screenshot per step. The screenshots are rendered by the wizard itself into
`Docs/img/wizard/`, regenerated by a make target, committed so GitHub shows them, and
checked for drift by the unit-test suite so a changed screen cannot leave a stale picture
behind.

## Context

Today the README is the only player documentation: about 250 lines that mix the pitch,
the build, and a reference for every feature, in the order the features were added.
`AGENTS.md` is written for coding agents and stays that way. There is no picture of any
screen anywhere in the repository except the hero image `Docs/img/screen.png`.

Two facts shape the screenshot side:

- Screens are never captured from the display. Pixels are read from inside the program,
  the way `PJ64_FRAME_DUMP` reads the emulator's back buffer. A screen grab once caught a
  private video call; that rule is not negotiable.
- The wizard already has a headless drive: `--selftest <path>` walks the real screens
  with synthetic SDL events, no window, no camera. Its draw code uses four renderer calls
  (`SDL_RenderFillRect`, `SDL_RenderDebugText`, `SDL_SetRenderDrawColor`,
  `SDL_SetRenderScale`), all of which SDL's software renderer supports.

A probe against the installed Homebrew SDL 3.4.16 confirmed that `SDL_CreateSurface` plus
`SDL_CreateSoftwareRenderer` plus `SDL_RenderDebugText` plus `SDL_SavePNG` run with no
`SDL_Init` call at all (`SDL_WasInit(0)` reports 0 afterwards), and that two runs write
byte-identical PNG files. `SDL_SavePNG` exists since SDL 3.4.0. The `deps` stage today only prints the SDL3
version; it gains `pkg-config --atleast-version=3.4 sdl3`, so an older SDL fails at the
first stage with a clear message rather than as a missing symbol at link time.

## Non-goals

- Screenshots of a running game, the grid or the mouse panel in play. They need a ROM
  at generation time and put game imagery in the repository. The hero image stays as it
  is; nothing else of the emulator is pictured.
- Any change to what the wizard's screens show or how they behave. If a screen turns out
  to photograph badly, that is a separate decision with its own spec.
- A documentation site, HTML output or any generator beyond Markdown that GitHub renders.
- Rewriting `AGENTS.md`. It gains the new flag and targets, nothing more.

## Part 1 — The guide

**Audience and voice.** A player who has cloned the repository and will not read the
code. Second person, imperative, short sections, every command copy-pastable as shown.
Environment variables are named where they matter and collected once in a reference
table at the end, so prose sections do not each carry their own list.

**Sections, in order.** Each names its source of truth; the writer verifies every fact
against it rather than against the README, which is being retired as a reference.

1. *Before you start.* Apple Silicon, Xcode command line tools, the three Homebrew
   packages, `make -j8 all`, `make test` and what its passing output looks like.
   Source: `Makefile`, `AGENTS.md`.
2. *Your ROMs.* No game data ships; the `Roms/` convention; accepted formats; there is no
   ROM browser. Source: `README.md` "Game files", `Source/Project64-sdl/main.cpp`.
3. *Playing a game.* `make run rom=…`; the built-in keyboard table and its gamepad pair,
   as a table of the fifteen controls; how the window closes; where the interpreter-only
   limit shows (speed is fine, the recompiler is off). Source: the default table in
   `Source/Project64-sdl/InputConfig.cpp`.
4. *Several games at once.* Grid mode, the strip, the 1 to 16 limit, muted tiles, Escape.
   Source: `Source/Project64-sdl/GridHost.cpp`.
5. *Bindings by hand.* The YAML grammar, one input per control, a listed control loses
   its pair, a bad file is ignored whole with one stderr line, `PJ64_INPUT_YAML`.
   Source: `InputConfig.cpp`, `Config/input.yaml`.
6. *The binding wizard.* A walkthrough in the order the screens come, one screenshot per
   step, using the file names fixed in Part 2: starting point, a control at rest, arming
   a key, the bound result, what happens without a gamepad, picking a panel slot, the
   gesture list and the camera, the six stick forms, the review with its inherited marks,
   saving beside a ROM, and the warning that guards `Config/input.yaml`. Ends with how the
   file is checked before it is written. Source: `Source/Project64-wizard/Screens.cpp`.
7. *Playing with a mouse.* The 640x640 window, the game image as the stick, click as a
   button, the panel, the flick gate, the shipped layouts and `input=`. Source:
   `README.md` "Playing with a mouse", `Source/Common/PointerLayout.h`.
8. *Playing with your face.* The camera prompt and who it is attributed to, privacy
   (frames never saved, shown or logged), the eleven gestures with their panel tags, the
   head stick, the threshold variables. Source: `README.md` "Playing with your face",
   `Source/Project64-sdl/FaceTracker.mm`.
9. *A layout per game.* Lookup order (beside the ROM, then `Config/mouse/`), the
   `input layout:` stderr line, why `Config/face/` is outside the lookup, `make config`
   replacing installed copies, `PJ64_FACE=0` for unattended runs. Source:
   `Source/Project64-sdl/GameConfig.cpp`, `AGENTS.md` traps.
10. *When something goes wrong.* Camera denied; a black window and the frame-dump check;
    "uCode crc not found" and data files beside the binary; a mapping file the reader
    rejects; a nod or tilt that reads backwards is a code fix, not a layout fix.
    Source: `AGENTS.md` traps.
11. *Reference.* Two tables: every `PJ64_*` variable with one line each, and every
    player-facing make target. Source: `grep -r getenv Source`, `make help`.

**Images.** Referenced as `img/wizard/<name>.png` relative to `Docs/`, each with alt text
that says what the screen is, so the guide reads without them.

**README afterwards.** Hero image, the one-paragraph pitch, prerequisites and the build
block, one sentence pointing at `Docs/UserGuide.md`, the "What works" paragraph trimmed
to its two limits, and the license line. Everything else moves to the guide and is not
duplicated: each fact lives in one place.

## Part 2 — The screenshot generator

**The flag.** `Project64-wizard --screenshots <dir>` joins `--selftest` and `--version`
in `Source/Project64-wizard/main.cpp`. It writes one PNG per stop into an existing
directory and exits non-zero, naming the file, if any write fails. It never calls
`SDL_Init`, never creates a window, and never starts the tracker. The event helpers the
self-test already has (`KeyEvent`, `ClickEvent`, `TextEvent` and their siblings) are
shared, not duplicated.

**Rendering.** An 800x640 `SDL_PIXELFORMAT_RGBA32` surface, the size `Screens.cpp` lays
out against, wrapped in `SDL_CreateSoftwareRenderer`. Each capture clears to the window
loop's background colour, calls `WizardDrawScreen` with the same arguments the loop
passes, presents to flush the batch, and saves with `SDL_SavePNG`.

**The tour.** A fixed table of stops, each a file name and the events that lead to it,
driven through `WizardHandleEvent` exactly as `--selftest` does. Gestures and the tracker
state reach the picture only through `WizardDrawScreen`'s last two arguments.

| File | What is on screen |
|---|---|
| `01-base.png` | The starting-point list, the built-in bindings highlighted. |
| `02-control.png` | Control 1 of 15, A, at rest, showing its inherited key and button pair. |
| `03-key-armed.png` | After `1`: the prompt to press a key. |
| `04-key-bound.png` | After `X`: A now reads `key X`. |
| `05-no-gamepad.png` | After `2` with no gamepad: the refusal in the message line. |
| `06-zone.png` | On Z, after `4` and a click on `mid1`: the half-scale panel with the slot taken. |
| `07-gestures.png` | On Start, after `5`, with mouth-open lit and the tracker dot filled. |
| `08-stick-forms.png` | On Stick, after `1` and four Downs: the six forms, `head-digital` highlighted. |
| `09-review.png` | The review, with the inherited controls marked. |
| `10-save.png` | The save screen aimed beside a typed ROM path, showing the derived file name. |
| `11-save-warning.png` | The four-line `Config/input.yaml` warning and its "Enter again" message. |

The tour never saves a file. Stop 10 stops after typing ends, before the second Enter;
stop 11 is never confirmed. There is no "Saved." picture: the guide describes that line
in words.

**Determinism.** Same SDL build, same bytes: the software rasteriser, a fixed window
size, a fixed font, no clock, and no machine-specific text. The last point is a rule the
tour must keep: the base screen's first row and typed save paths only. Choice 1 on the
save screen prints `SDL_GetBasePath()`, which differs per checkout, so the tour never
selects it. Typed paths use a neutral home such as `/Users/you/Roms/…`. A Homebrew SDL
upgrade that changes the debug font or the PNG encoder will show up as drift; the answer
is to regenerate and commit, and the check's failure message says so.

## Part 3 — Make targets and the drift check

- `make wizard-screenshots` (depends on `wizard`): creates `Docs/img/wizard/` if needed
  and runs the flag on it with `PJ64_FACE=0`, for symmetry with the self-test even though
  the flag ignores the variable. Listed in `make help`.
- `make wizard-screenshots-check` (depends on `wizard`): `Scripts/wizard_screenshots_check.sh`
  renders into a temporary directory, compares every file byte for byte against
  `Docs/img/wizard/`, and fails on the first difference or on a file present on one side
  only, printing the file name and "run make wizard-screenshots and commit the result".
  Passing output is one `ok:` line.
- `make unit-test` runs the check after the five unit binaries. It is headless, so it
  belongs there. `make test` is unchanged.
- `AGENTS.md`: the command list gains the two targets; the wizard paragraph gains the
  flag; "Verifying a change" tells an agent that touching `Screens.cpp` means
  regenerating the screenshots.
- The spec's plan lives beside it in `Docs/superpowers/plans/`.

## Open risks

- The guide's key table and variable reference are copied facts. They are verified once
  at writing time against the code, and nothing checks them afterwards. A later change to
  the default table or a new `PJ64_*` variable will need a matching guide edit; the trap
  list in `AGENTS.md` says so.
- Eleven 800x640 PNGs of mostly dark background with 8x8 text should be a few kilobytes
  each; the probe's near-empty frame was 4 KB. If a real screen comes out much larger the
  format is still right, only the estimate was wrong.
- The drift check pins the pictures to the SDL build. That is the intended trade: a
  false failure after a Homebrew upgrade costs one regenerate, a silently stale screenshot
  costs a reader's trust.

## Changed during implementation

This section records where the shipped code diverged from the text above. The text above
is left as originally written; this is appended, not a correction of it.

- Stop `06-zone.png` is taken after pressing `4` a second time, not straight after the
  click. `CaptureZone` leaves zone mode the moment a slot is taken, so the panel is no
  longer drawn then; pressing `4` again redraws it with the taken slot labelled, which is
  the picture Part 2 describes. Escape then leaves the mode before the tour moves on.
